Read the following notes about serving large language models and answer the question at the end.

Serving a large language model involves two phases with very different resource profiles. During the prefill phase the server processes the whole prompt in a single forward pass: every token attends to every previous token, so the phase is dominated by matrix multiplications and is bound by the compute throughput of the GPU. The output of this phase is the first generated token and the key-value cache, which stores the attention keys and values of every prompt token for every layer of the model. During the decode phase the server generates the remaining tokens one at a time. Each step reads the whole key-value cache and the model weights from GPU memory but performs relatively little arithmetic, so decoding is bound by memory bandwidth rather than by compute.

When both phases share the same GPUs, long prompts arriving in the prefill phase stall the token generation of the requests that are already decoding, and the inter-token latency becomes unpredictable. Disaggregated serving runs the two phases on separate pools of GPUs, often on separate nodes, so that each pool can be sized and tuned for its own bottleneck. The price is that the key-value cache computed by a prefill worker must be moved to the decode worker that continues the request. For a model with tens of layers and a prompt of a few thousand tokens the cache easily reaches hundreds of megabytes, so the transfer has to bypass the CPU and go straight from GPU memory to GPU memory, for example with RDMA over an InfiniBand fabric. Libraries such as NIXL expose these transports behind a common interface, and the inference server only has to tell them which cache blocks to read from which remote worker.
